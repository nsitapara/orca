# Pilot hooks into upstream Orca

Every change Pilot makes to an upstream file is listed here (D24). Each one is an import plus one call, one JSX element, or one config line. The logic lives in `src/packages/pilot/`. `node src/packages/pilot/scripts/hook-guard.mjs` checks that every row's file still contains its Match text, and that no other upstream file differs from `upstream/main`. After an upstream sync, a failing row names the file to fix.

Which hooks were added for "Show all tabs in Activity", and why:

- `activity-tabs-row-type`, `activity-tabs-rows`, `activity-tabs-row-key`, `activity-tabs-row`, `activity-tabs-header-count` and `activity-tabs-count`: the option is a filter on Activity's one list, not a second section (Nish, 2026-10-17). Tabs are rows in the agents' groups, so they share the scroll, the sticky headers, collapse and Group by. The tabs ride on each group object through a WeakMap in `activity-tabs-rows.ts`, so upstream's group type is unchanged and every hook returns upstream's value until a group carries tabs.
- `activity-tabs-group-header`, `activity-tabs-nest` and `activity-tabs-thread-icons`: grouped by worktree, a group's sessions were hard to tell from the next worktree's, and a row's first icon was its state, not its agent (Nish, 2026-10-17). Each hook wraps upstream's own element and renders it unchanged until Pilot attaches; the nest sits inside the row's spacer because that spacer is the context menu's `asChild` trigger.

Which hooks were added for "Hide terminals", and why:

- `activity-tabs-filter-menu` and `activity-tabs-filter-count`: with "Show all tabs" on, plain terminals (a dev server, a stack) crowd the agent sessions (Nish, 2026-10-19). "Hide terminals" is a filter, so it sits in the Filters section with upstream's Hide items and counts toward the options badge. It is offered only while "Show all tabs" is on, since only then does the list hold terminals. A terminal counts as an agent by `resolveOpenTabOccupantAgent`, the tab strip's identity rules that tab search already uses. Both return upstream's value until Pilot attaches: the item renders nothing and the count is 0.

Which hooks were extended for "Hide automation runs", and why:

- `activity-tabs-filter-menu`, `activity-tabs-filter-count` and `activity-tabs-threads`: Pilot's automation sessions fill Activity, and one may not always want to see them (Nish, 2026-10-20). It is a filter like "Hide terminals", offered whenever Pilot is attached since agent sessions always list. A row counts as an automation run when a Pilot step ran in its tab: the step table records each step's pane key (`<tabId>:<leafId>`), and `pilot.runs.automationTabs` answers for the tab ids it is given, asked of the Pilot on the row's host. A "no" is asked again for a minute, because a step records its pane only after its tab opens; a host that refuses (unreachable, or a build without the method) leaves its rows shown.

Which hooks were added for links and stack ports, and why:

- `activity-tabs-footer-label`: grouped by worktree, a row's footer repeated the worktree name its header shows (Nish, 2026-10-19). The wrapper reads the row's group from a context `ActivityTabsNest` provides and, under a worktree, shows the MR and Linear chips Cove shows. Each worktree header fetches them once (the hover card's own lifecycle effects, 60 s cache), so rows only read the caches. Grouped otherwise, or before Pilot attaches, upstream's name renders.
- `activity-tabs-hover-card`: the card led with the session summary its row already shows, and its links and ports came last (Nish, 2026-10-19). Reordering upstream's JSX would be more than a hook, so Pilot renders its own card from upstream's exported sections and the same data hooks (`use-hover-card-details.ts` mirrors the wiring), and upstream's card renders until Pilot attaches. The stack's ports come from the worktree's `.env.ports`, read through `readRuntimeFileContent`. An SSH worktree's file can't be read from the desktop, so its card keeps upstream's Live Ports list.

Which hook was added for the browser version, and why:

- `web-renderer`: the browser version (the web client `--serve` hosts) has its own entry, `src/renderer/src/web/main.tsx`, which never runs the desktop's `attachPilotRenderer()`, so Pilot's sidebar items and pages stayed hidden there. The hook wraps the entry's lazy app-shell import, `lazy(() => withPilotWebRenderer(import('../App')))`, instead of a top-level call. Pilot's attach then loads as its own chunk next to the shell, after `installWebPreloadApi()` has run in `WebRoot`'s render, and finishes before the shell renders; a failed attach logs and the shell still loads. The connect screen, shown only when pairing by hand, keeps Orca's name. Upstream's `I18nProvider` already puts `@/store` in the web startup chunk, so the hook doesn't change when the store evaluates.

Which hooks were added for machine tags, and why:

- `activity-machines-list`, `activity-machines-page` and `activity-machines-chip`: Activity lists every machine's sessions, so a row says where it runs (Nish, 2026-10-17). A drop-in for `ActivityThreadListPane` decides once per list whether its rows span machines, and provides a context that the footer chip reads. Upstream's types and the memoized rows are unchanged, and nothing renders until Pilot attaches.
- `activity-project-scope` and `activity-project-filter`: a project filter used one machine's repo id. The saved filter stays repo ids; Pilot widens it by project identity when it reads it, and lists each project once. Repos without a remote stay per machine. Both are inert until Pilot attaches: `useActivityProjectRepoIds` returns its input untouched, and `ActivityProjectFilterSection` renders upstream's own section while `pilotStore()` is null.

Which hook was added for the startup hang, and why:

- `tray-after-launch`: on 2026-10-13 the packaged app hung for good in `-[NSStatusItem setMenu:]`, which upstream calls on the tick after ready-to-show (stablyai/orca#17045). The hook is the import and one line, `const createTray = deferTrayPastLaunch(window, createSystemTrayDeferred)`. Pilot builds upstream's creator with its `tray-created` milestone, runs it 10s later on macOS (cleared if the window closes first), and ends the startup phases the window settles (`src/main/startup/`).

## After an upstream sync

Run the guard, then the upstream tests next to every hooked file (R10). Those are the folders of the `src/` files in the table above. The renderer root `src/renderer/src` is left out: its hook, `attachPilotRenderer()`, is covered by Pilot's own attach tests.

    node src/packages/pilot/scripts/hook-guard.mjs
    HOOK_DIRS=$(node --input-type=module -e "import {readFileSync} from 'node:fs'; import {dirname} from 'node:path'; import {parseHooksTable} from './src/packages/pilot/scripts/hook-guard.mjs'; const rows = parseHooksTable(readFileSync('src/packages/pilot/HOOKS.md', 'utf8')); console.log([...new Set(rows.map((r) => dirname(r.file)).filter((d) => d.startsWith('src/') && d !== 'src/renderer/src'))].join(' '))")
    ORCA_CLI_INSTALL_PATH=$(mktemp -u)/orca ORCA_BROWSER_EXECUTABLE= pnpm exec vitest run --config config/vitest.config.ts $HOOK_DIRS src/cli/handler-group-manifest.test.ts

Which hook was added for orphaned browser hosts, and why:

- `vitest-orcad-sidecar-sweep`: upstream's `orcad-serve-parity.integration.test.ts` (it runs when `out/orcad` is built) starts orcad, which starts `/Applications/Orca.app --serve` as its browser host, then SIGKILLs orcad. The host outlives it, listens on every interface and blocks Orca's updater ("Close the other Orca instances"). The hook is one `globalSetup` line; `test/orcad-sidecar-sweep.ts` runs before and after each run and stops only `--serve` processes on an `orcad-browser-*` profile whose parent is gone and whose environment has `ORCA_VITEST_RUNTIME`, then removes their `/tmp` profiles.

Which hooks were added for the YAML engine, and why:

- `right-sidebar-badge`: the activity bar's own slot is a status dot with no count, fed from a memo Pilot can't refresh.
- `orca-automations-off`: the desktop app and `serve` never start Orca's automation service, and nothing turns it back on. Pilot's `orcad` keeps upstream's engine.
- `agent-launch-env` (required): carries each agent terminal's environment and its agent arguments (a pinned session id, `--resume`, `codex resume <id>`, a step's `args`) through one call, so upstream's `extraAgentArgs` allowlist isn't used for them.

Which hooks were added for card details, and why:

- `sidebar-waiting-item`, `sidebar-automations-active` and `sidebar-automations-open`: the Inbox item under Automations, its highlight rule, and the Automations click that leaves it. They are three one-line hooks in `SidebarNav.tsx` and add no `activeView`; the card Details themselves live wholly in Pilot's folder.

Which hook was added for reading skills, and why:

- `skill-open-file`: upstream's skill details can Reveal a skill's file or copy its path, but not open it. Nish wants the skills a job uses to be easy to read (2026-10-15), so Open puts the SKILL.md in the floating workspace's editor, as the OS's "Open With" does, and closes the details. The hook is the import and one JSX element; `OpenSkillFile` renders nothing until `attachPilotRenderer()` registers the store, so upstream's skills tests see the dialog as it was.

Which hook was added for sidebar theming, and why:

- `right-sidebar-appearance`: upstream's appearance setting (Default, Match Terminal, Tinted) styles only the left sidebar, so with Match Terminal the right sidebar kept the app's default surface. Nish wants both sidebars to match the terminal theme (2026-10-16). The hook is the import and one call; it puts the variables from upstream's `resolveLeftSidebarStyleVariables` on the right sidebar's root and does nothing until `attachPilotRenderer()` registers the store. The same attach relabels the setting "Sidebar Appearance" (English only) through its i18n post-processor, so no catalog string is edited.
- No new hook for whole-window theming: with Match Terminal, the center column, tab bar, status bar, popovers and dialogs kept Orca's default surfaces, and Nish wants the theme consistent across the window (2026-10-17). `attachPilotRenderer()` (the existing `renderer` hook) puts the same terminal variables, plus `--popover` and `--secondary`, inline on the document root. `appearance/window-appearance.css` swaps the glass background that Orca's popover, menu and dialog primitives hard-code, matched by its exact class text; a test fails if upstream renames those classes. The same stylesheet raises every divider to a 22% foreground mix (Orca's 7% vanishes on a terminal theme), and draws the sidebar seam from the sidebar column, top to bottom, because the sidebar and the page beside it now share one surface (2026-10-17).
